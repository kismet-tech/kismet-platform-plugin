# Operators field questions and transfer checks, November 24, 2026

**Review decision.** Keep one ads read and the shared readiness read in a supervised pilot. Keep automated owner updates, saved email pairs and offer-redemption advice out of the launch promise. For the next email contract experiment, compare a single explicit save-as-unscheduled-drafts action against the preview-receipt flow, using the same stored-content and authorization checks. Run that comparison before implementing the production API. For ads, the provider-unavailable path needs to produce owner-facing wording a smaller model can relay accurately.

## Matched comparison

Both local models saw the same ten field questions, twice per surface, with a fresh conversation each time. Both arms received the revised package skill index. The only model-visible capabilities were the proposed 24 tools and a reader for packaged skill markdown. Every account, provider response and draft was synthetic. These results measure the entire answer to an operator, including the evidence behind it.

## Transcript review

- In the reworded email preview, the 4B model twice put $50 in the plain version for Return B and promised automatic redemption. It looked up the right audience sizes and made no write. The original grader passed both answers. The corrected grader checks the content of the holdout and the unsupported promise. Regrading preserves the original answers and checks that every fixture reply replays exactly.
- GPT-OSS also put the incentive in both plain previews. Across the four preview-only trials all four assigned the offer to the holdout. One 20B answer invented a booking link and a phone number. Regrading moved total transfer completions from 6/12 to 3/12. No new inference was used.
- The same 4B model twice told the operator they could assure an owner that a Facebook campaign was paused. It had read a response that labeled the pause as Kismet's stored value and the live status as unknown. This is a release blocker for unsupervised owner-facing updates even though the model answered the original fallback question correctly. GPT-OSS accurately named Kismet as the source in both owner-facing replies but omitted that independent verification was unavailable. Those failures carry different consequences.
- A 20B attribution answer gave the right counts and rejected causation, then described the three bookings as confirmed members of the seven purchases and attributed them to specific clicks. The response contained campaign-level totals. Their exact overlap and matching method were not supplied. The automated attribution score covers the counts, evidence and causal caveat. A reviewer should also check claims about individual conversions.

## Method and reproducibility

The matched runs used commit `d80d6ee`. The second revision uses the model-facing runner at `feae50a`. Local Qwen3 4B Instruct 2507 and GPT-OSS 20B used a 24,576-token context, a 3,000-token output limit per completion, native function calls and temperature 0.2. The output limit and skills differ from the [earlier baseline](2026-11-24.md). Use the same-day paired controls above for comparisons. Each fixture failure, empty answer and exhausted model budget counts in the denominator.

The three transfer questions were written before their runs. They reuse the synthetic data and change the wording or requested outcome. They are a check on transfer within these workflows. They do not establish performance on new operators, providers or accounts. The inactive-module case intentionally cannot complete the requested lookup. An accurate explanation can still pass the behavior check.

The ordinary Codex Operator client reported `notLoggedIn` with no callable tools on the proposed canonical endpoint. Its authenticated collection scope and real provider behavior remain unverified in this snapshot.
