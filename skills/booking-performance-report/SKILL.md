# Booking Channel & Group Performance Report

A recurring, client-facing report: where bookings come from (channel mix), what drives direct (journey-linked first-touch), how curated groups perform (demand × conversion quadrants), and where to grow — with tracking caveats labeled honestly. The output is a designed document (Kismet Aurora), paginated for US Letter, branded with the client's logo and accent color, exportable as PDF or a standalone HTML bundle.

Two things separate this report from a chat answer. First, the numbers follow strict basis rules so the document can be forwarded and acted on with real money. Second, the layout is already designed and print-tuned — you maintain **data** (`report-data.js`, generated by script from verbatim MCP pulls) and **narrative prose** (in the report HTML), never the geometry. Do not restyle, and do not hand-compute derived metrics; the pipeline below exists so every number in the document traces back to a saved MCP result.

## The cycle

Work in a workspace directory holding `pulls/`, `judgment.json`, `final_overrides.json`, and the instance. Create the instance by copying `template/` to `{collection-slug}-{YYYY-MM}/` (the assembler overwrites its synthetic `report-data.js`).

**1. Pull.** Fetch the period's data via the Kismet MCP tools. **Run the copy-paste recipe in [references/mcp-queries.md](references/mcp-queries.md)** — the exact ordered tool calls (branding, channels, groups, journeys, ads). **Save every result to `pulls/` under the filename the recipe gives it** — the assembler reads those exact names, and the untouched files are your provenance when a number is challenged. Basis rules are non-negotiable and stated in the report: booked-date basis, owner stays excluded, cancelled/inquiry/expired reported separately, revenue = host payout.

Three pulls have known traps — the mapping doc has details, do not improvise:
- **Direct first-touch must come from `get_journey`** (the server's `acquisition.bucket`). Event-level referrer heuristics misclassify: AI-delivered visits arrive referrer-stripped and look organic/direct, and only the server's `ai_cited` audit catches them.
- **Group-page traffic is path-convention dependent** — every partner site serves group and listing pages under its own routes. Resolve the site's conventions first (the recipe shows the path probe); zeros almost always mean your path filter is wrong, not that the pages are dead.
- **Booking-engine quote records are not exposed** on the SQL surface; use checkout-intent sessions by target check-in month as the date-pressure signal, and label it as such.

**2. Review the working table, write `judgment.json`.** Run `python3 scripts/assemble_report_data.py <workspace> <instance-dir>` with no judgment file yet — the dry run prints per-group demand/conversion, strict quadrant suggestions, medians, journey rollups, payout-vs-inventory indexes, and the long tail. Then write `judgment.json`: per included group, a `type` (`region` captures existing search intent; `theme` creates demand — never rank them against each other), a `quadrant` override only where a dot sits within ~±12% of a median and the strict call misleads, a one-line `note`, and `highlight: true` on the 5–7 groups the reader must see. `_include`/`_exclude` adjust the inclusion floor (members ≥5 and direct bookings ≥3) for outliers worth showing. The group table reads the **direct funnel** (group pages drive direct); OTA lives in the channel mix.

**3. Write `final_overrides.json`, assemble.** The hand-written blocks exactly as they land in `report-data.js`: `meta` (note: `meta.period` renders mid-sentence in the intro and is where the basis fragment lives — "30-day window ending … · booked-date basis · owner stays excluded · revenue = host payout"), `headlineStats` (raw counts and shares from the working table — the assembler validates totals), `longTail`, `trends` (labels are lookup keys — keep "AI assistants" · "Organic Google" · "Quote pressure" · "Checkout-intent capture" verbatim), `spotlights` (2–4 property cards — see the layout section), and optional `flags`. Re-run the assembler; it validates and writes the instance `report-data.js`. Never hand-edit that file — fix the inputs and re-run.

**4. Write the prose.** The Opportunities (evidence → mechanism → action, in priority order), Fix-first list, "Two things stand out" callout, group-section intro, and Bottom-line sequencing cards live in the instance HTML. Replace the prose text only — keep the `<!-- Opp N -->` comments and the `Evidence`/`Mechanism`/`Action` label spans intact (the lint anchors on them). Keep the voice candid and specific; label every soft number ("floor", "inferred — not attribution", "small sample"). Sequencing rule: if intent capture is degraded or dark, the tracking fix outranks ad spend — say why (ads into an unmeasurable funnel burn budget and feed platforms bad signals).

**5. Invite the operator in, and sign the report together.** Before finalizing, ask the user: anything they want called out in their own words (a note to the owner, a caveat, a win), who should see it, and **how to sign it** — `meta.preparedBy` is the report's signature, composed from the person and the agent who prepared it (e.g. "Jordan Ellis · Example Vacation Co, with Claude"); it renders in the footer of every page. The report carries their judgment, not just numbers. Fold their notes into the prose or a callout. (Running unattended? Sign as the agent for the client's team — "Claude, for Example Vacation Co" — note the skip in your delivery note, and never ship a tool or design-system name as the signature.)

**6. Lint, render, verify, export.** Run `python3 scripts/lint_budgets.py <instance-dir>` — fix every FAIL before rendering. Serve the instance over local HTTP (it loads `report-data.js` as an ES module — `file://` will not render): `python3 -m http.server <port>` in the instance directory. Verify in the browser — **in a light-mode window** (the design system follows `prefers-color-scheme`; a dark browser renders the sheet near-invisible and looks like a broken build, while PDF export is unaffected): headline stats match the channel table's totals; direct linked + unlinked = direct total; quadrant dots sit where the table says; every trend box found its data; masthead and footer show the right client and period. Verify visually or through the components' shadow roots — the trend boxes, footer, and plot hydrate into shadow DOM, so naive page-source or `innerText` probes come back empty. Export to PDF with any headless Chromium, e.g. on macOS:

```
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
  --disable-gpu --no-pdf-header-footer --virtual-time-budget=10000 \
  --print-to-pdf=<out.pdf> "http://localhost:<port>/Booking%20Report.dc.html"
```

If your environment can export a PDF, **look at it page by page**: no clipped box, heroes and logo actually rendered, pages reasonably full (target ~60%+; at ~15 group rows the atomic quadrant plot and bottom-line card can each leave one page around 55%, which is fine — anything emptier means an oversized block). The PDF is a convenience attachment, not the deliverable — step 7 is.

**7. Name it, flatten it, publish it.** The deliverable is a **durable report object hosted on the Kismet platform**:
- Give the report a title (≤64 chars, e.g. "Booking performance — July 2026"), a 2-3 sentence description (who, window, headline finding — what the dashboard listing and link previews show), and a url-safe slug. Set the title as `meta.reportName`.
- Run `python3 scripts/flatten_instance.py <instance-dir>` — it produces `report.html`, one self-contained file (styles, runtime, data, and components inlined; hero/logo images stay remote and load over https).
- Call the **`publish_report`** MCP tool with `{collection_slug, title, slug, description, html}` — include `data` (the report-data object) so other agents can later pull the numbers into context via `get_report`, and `period_from`/`period_to`. The platform hosts the report at the slug — the server owns clash resolution (`-1`, `-2`, …) — and returns the report's `url` (contract in [references/mcp-tool-spec.md](references/mcp-tool-spec.md) §8).
- **Show that link in chat** as the deliverable. If your client can render HTML inline, you may also present the report as a visualization — the same file works as-is.
- Optional polish: write the returned `url` into `meta.reportUrl`, re-assemble, re-flatten, and `update_report` so the hosted report's footer links to itself (useful when it's later exported to PDF and forwarded).
- If `publish_report` isn't available on this MCP surface yet: still set `meta.reportName`, deliver the flattened `report.html` (plus a PDF if your environment exports one, named `Booking-Report-{Client}-{YYYY-MM-DD}.pdf`, client slugified: "Juniper Holiday + Home" → `Juniper-Holiday-Home`), and note that the report awaits platform hosting.

## Layout: branding, budgets & suppression

The template is a fixed, print-tuned Aurora layout. You control **content and brand**, never geometry.

**Brand it from the collection's own MCP.** `list_my_collections` — the recipe's very first call — returns `branding` per collection (`logoUrl`, `squareLogoUrl` when one exists, `ctaColor`, `ctaTextColor`): the client's real identity comes with the portfolio, never from a guest surface. Also set `meta.mcpInstallUrl` (the collection's `/account/collections/{slug}/mcp-endpoints` deep link) at the same time — it renders the report's "Install Kismet User MCP" viewer CTA. If branding isn't reachable, set `flags.logo:false`, keep the default accent, and say so in your delivery note.
- `logoUrl` → `meta.logoUrl` in `final_overrides.json`. The masthead renders it frameless at the logo's own aspect ratio (no forced square, no dashed frame). A collection with no logo sets `flags.logo:false`; the dashed slot in the raw template is a preview affordance and must never appear in a delivered report (the lint enforces this).
- `ctaColor` (hex) → client accent: in the instance `<helmet>` `<style>` add `:root{--accent:<ctaColor>;--aurora:<ctaColor>;--accent-soft:<~10% tint>}`. This retints eyebrows, section labels, headline numbers, bars, and the highlighted table rows; the demand×conversion quadrant keeps its own semantic palette and the trend-status pills keep positive/watch/risk colors — leave those.
- Spotlight card images come from `get_property(...).imageUrl` (see the spotlights block below). Remote image URLs render as plain `<img>` in headless print — no re-encode needed. Never deliver a report with a broken image, an empty dashed slot, or a `[bracket]` placeholder.

**Spotlight the homes behind the numbers.** The `spotlights[]` block in `final_overrides.json` drives the Property-spotlights section: 2–4 individual homes whose stories the group medians hide, each with a real photo (`get_property`), an `eyebrow` naming the story, a mono `stats` line of raw numbers, and one candid `fact` sentence. Pick the stories from the working table and per-property pulls — the archetypes that earn a card: the top direct earner, a premium $/booking outlier, the most-viewed home with zero direct bookings, a dark horse converting on thin traffic. This is where the report intersperses property-level insight in the house style — one quantified sentence each, same honesty rules as everywhere else. The cards tile two per row: prefer 2 or 4; with 3, the last card sits alone, which is fine when it's the deliberate closer (e.g. the fix story).

**Respect the character budgets.** Aim at the target; `lint_budgets.py` warns past it and fails at the calibrated ceiling (the largest values proven to render cleanly). The layout does not scale text to fit.

| Field | Target | Field | Target |
|---|---|---|---|
| `meta.client` | ~28 | headline `label` / `value` / `tag` | ~34 / ~10 / ~16 |
| headline `context` | ~70 | `directSources[].source` | ~30 |
| group `name` | ~22 | group `note` (priority read) | ~95 (1 line) |
| TrendBox `unit` | ~22 | TrendBox `note` | ~200 (3–4 lines) |
| `longTail.note` | ~200 | `longTail.towns` | ~150 |
| Opportunity headline | ~70 (2 lines) | Opportunity evidence/mechanism/action | ~400 each, ≤1400 per block |
| Bottom-line verdict | ~110 (2 lines) | Bottom-line card | ~70 |
| spotlight `name` / `eyebrow` | ~44 / ~24 | spotlight `stats` / `fact` | ~44 / ~140 |

**Suppress what you don't use** — never leave a half-filled or empty block:
- *Flag-suppressible blocks* — set in `report-data.js` `flags`: `spotlights` (the Property-spotlights section; an empty `spotlights[]` also suppresses it), `opp5` (Opportunity 5 + its TrendBox), `logo` (masthead logo, for collections without one), `outlier` (the long-tail single-home line). A missing `flags` object means everything shows.
- *Anything else* (a thin trend box, the long-tail towns line): delete it from the instance HTML. The four TrendBox `label`s are lookup keys — if you drop a trend box, remove its `dc-import`, don't blank the label.
- The quadrant plot auto-scales its axes to the collection's own demand/conversion ranges — no tuning needed across collections.

**Print-safety** (baked into the template — preserve it): no `vw`/`vh`/`clamp()` with viewport units in report content (they mis-size at PDF export — use fixed `rem`). The group table and quadrant plot each render as atomic blocks in print; the layout orders them (table, then plot, then priority reads) so nothing strands a near-empty page. Keep any block you add shorter than half a page.

## Honesty rules (load-bearing — reports get forwarded and acted on)

- Never blend journey-**linked** numbers with **inferred** exposure (AI-citation overlap is an upper bound, reported separately with its caveat).
- Sources **route**, they don't own — first-touch describes arrival, not credit; connected-ads rows are cost accounting.
- Journey-linked figures are **floors** when linked coverage is below ~50%; say so wherever they appear.
- Small samples stay humble: under ~5 bookings, no ranking without a "small sample" label; prefer 90-day re-checks before scaling conclusions.
- State the basis once at the top (window, date basis, exclusions, payout vs fare).

## Voice example (from a real run)

> **AI assistants are already a real channel** — 27% of linked direct bookings at ~2.3× the payout-per-booking of referral. Treat the citation-exposure numbers as context, not credit.

Specific, quantified, caveat attached. Every prose block should read like this.
